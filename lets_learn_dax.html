Most DAX tutorials hand you a single flat table and ask for a SUM. Real Power BI work starts earlier than that: you're given a pile of raw tables, you decide how they connect, and only then do the numbers start meaning anything. That's the order this course follows too.

Learn DAX: the mindset before the syntax

DAX looks like Excel formulas at first glance, and that resemblance causes most of the early confusion. Excel formulas point at cells. DAX expressions point at entire tables and columns, and their result depends on what's currently in view — a concept called context. Get comfortable with that idea before you write a single measure, and the rest of this course gets much easier.

What DAX actually is

DAX stands for Data Analysis Expressions. It's the formula and query language behind Power BI, Analysis Services, and Power Pivot in Excel — one language, three products. You'll use it in two places: inside the data model, to define calculated columns, measures, and calculated tables; and in DAX query view, to write standalone EVALUATE queries that return a table, the way the Bonus section of this course does.

Two kinds of context

Almost every DAX surprise traces back to one of these two ideas:

  • Row context — when a calculation is being evaluated one row at a time, with access to the other column values on that same row. Every calculated column works this way, and so does an iterator like SUMX while it's walking a table.
  • Filter context — the set of filters currently narrowing down your data, coming from slicers, visual axes, and other filters on the report page. Every measure is re-evaluated for whatever filter context it's sitting in — that's why the same measure shows a different number in every cell of a matrix.
Why this matters immediately CALCULATE, the function you'll use more than any other, does exactly one thing: it changes the filter context before evaluating an expression. Nearly every intermediate and advanced technique in this course is really just a variation on "change the filter context, then aggregate."

The three building blocks

Every exercise in this course asks you to build one of these three things. They look similar in the formula bar, but they're evaluated at completely different times and stored in completely different ways.

Calculated column

Evaluated once per row, when the model refreshes. Stored physically in the table.

Reach for this when the result belongs to a single row and you'll want to slice, filter, or group by it — like a category label or a Yes/No flag.

Measure

Evaluated at query time, fresh for every filter context. Never stored — always recalculated.

Reach for this for anything that aggregates — a total, a ratio, a rank — that should update as someone clicks around a report.

Calculated table

Evaluated once when the model refreshes, like a calculated column, but it produces an entire new table.

Reach for this for a small reference or summary table that doesn't exist in your source data — a distinct list, a disconnected parameter table, or a summary built from measures.

The function families you'll actually use

DAX ships with over 250 functions, but a working data model leans on a handful of families. Here's the map — every function used anywhere in this course's exercises falls into one of these:

  • Aggregation SUM · COUNTROWS · DISTINCTCOUNT · AVERAGE

    Collapse a column or table down to a single number.

  • Filter & context CALCULATE · FILTER · ALL

    Change what's being filtered before an aggregation runs — the core of nearly every real measure.

  • Iterators SUMX · RANKX · MAXX

    Walk a table row by row to calculate something a plain aggregation can't reach — usually because the calculation needs values from more than one column at once.

  • Time intelligence TOTALYTD · SAMEPERIODLASTYEAR

    Shorthand functions for calendar-based comparisons, built on top of a proper Date table.

  • Relationship functions RELATED · RELATEDTABLE · USERELATIONSHIP

    Reach across a relationship you've already modelled to pull in a value from another table.

  • Logical IF · SWITCH · NOT

    Branch a calculation based on a condition — the same idea as an Excel IF, but usable inside a column, a measure, or a table.

  • Table-shaping DISTINCT · VALUES · ADDCOLUMNS · SUMMARIZECOLUMNS

    Build or reshape an entire table — the basis of every calculated table and DAX query in this course.

  • Information ISBLANK · SELECTEDVALUE

    Ask a question about the current context or a value — is it blank, is exactly one item selected — before deciding what to calculate.

The business case: RR Retail Analytics

RR Retail is a 12-store consumer electronics chain across four regions of India. The head of analytics wants a Power BI model that can answer questions about sales performance, store targets, product profitability, promotions, and returns — but so far all anyone has is exports from five different source systems. That's the workbook you're about to open.

Why it's built this way Nothing in the workbook is pre-joined and two of the tables don't line up cleanly on the same grain as the rest. That's deliberate — in a real job, source data never arrives pre-modelled either. Part of what you're practising is deciding how tables should relate, not just writing measures once someone else has decided for you.

Build the data model

Import all eight tables, then build the relationships below one at a time. Power BI will suggest some of these automatically — check its suggestions against this list rather than accepting them blindly, since cardinality and cross-filter direction matter for the exercises later.

Relationships to create

  • 1
    Date[Date] → Sales[OrderDate]1 : Many · Active

    The primary relationship for anything date-related. This is the one that stays active for ordinary time filtering.

  • 2
    Date[Date] → Sales[ShipDate]1 : Many · Inactive

    Power BI only allows one active relationship between two tables. This one and the next stay inactive until a measure calls USERELATIONSHIP — that's an Advanced exercise.

  • 3
    Date[Date] → Sales[DueDate]1 : Many · Inactive
  • 4
    Customers[CustomerID] → Sales[CustomerID]1 : Many
  • 5
    Products[ProductID] → Sales[ProductID]1 : Many
  • 6
    Stores[StoreID] → Sales[StoreID]1 : Many
  • 7
    Promotions[PromotionID] → Sales[PromotionID]1 : Many · Optional FK

    Roughly two-thirds of Sales rows have a blank PromotionID. The relationship still works — a blank simply doesn't match any Promotions row — but it's why SUM-based promotion measures need blank-aware logic (see Advanced).

  • 8
    Sales[SalesID] → Returns[SalesID]1 : Many

    A fact table feeding another fact table — Returns is really a child of Sales, not of a dimension.

  • 9
    Stores[StoreID] → Targets[StoreID]1 : Many
Leave Targets and Date unrelated — on purpose Targets is stored at store + month grain, not per day, and it has no Date column to join on. Don't force a relationship by, say, joining on a text year-month key — Targets doesn't have one row per day, so that relationship would silently double-count. Instead, the Advanced exercises show you how to reach across to Targets from a measure using CALCULATE and FILTER, without any physical relationship at all. This exact situation — a monthly plan/budget table sitting next to a daily transaction table — comes up constantly in real reporting.

A star schema, mostly

Once the nine relationships above are in place, Sales sits in the middle as your main fact table, with Customers, Products, Stores, Promotions and Date as one-to-many dimensions around it, and Returns hanging off Sales as a second, smaller fact table. Targets floats on its own, connected only to Stores. That asymmetry is normal — not every table in a real model joins the same way.

1 · Fundamentals

Calculated columns, a calculated table, and basic aggregations — the row-context-vs-filter-context distinction that everything else in DAX rests on.

Calculated column

Net line value

Every order line needs a value that already accounts for quantity, price and any discount. Add a column on Sales called Net Sales Amount.

Hint — Calculated columns are evaluated per row, so you can reference other columns on the same table directly — no CALCULATE needed.

Sales[Net Sales Amount] =
Sales[Quantity] * Sales[UnitPrice] * (1 - Sales[DiscountPercent])

Calculated column

Order size tier

Bucket every Sales line into a plain-language size label — "Single Item" for a quantity of exactly 1, "Bulk" for 4 or more, and "Small Order" for everything in between. Add this as a column called Order Size Tier on Sales.

Hint — You're choosing between more than two outcomes, so a single IF won't be enough on its own — nest one IF inside another, checking the more specific condition first.

Sales[Order Size Tier] =
IF (
    Sales[Quantity] = 1, "Single Item",
    IF ( Sales[Quantity] >= 4, "Bulk", "Small Order" )
)

Total net sales

Line items vs. distinct orders

Measure

Total cost of goods sold

Cost lives on Products, not on Sales. Build a measure for total cost that multiplies each line's quantity by that product's unit cost.

Hint — SUMX walks Sales row by row, and RELATED pulls a value from the one-side table (Products) through the relationship you built. SUM alone can't do this because Cost isn't a column on Sales.

Total Cost =
SUMX (
    Sales,
    Sales[Quantity] * RELATED ( Products[Cost] )
)

CALCULATE, time intelligence, ranking, and your first calculated table built from measures — the tools behind most of a typical Power BI report.

Measure

Completed sales only

Cancelled orders shouldn't count toward revenue. Build a measure that only totals lines where OrderStatus = "Completed", without touching your original Total Net Sales measure.

Hint — CALCULATE changes filter context. Passing a condition as its second argument overrides whatever filter is already there for OrderStatus.

Completed Net Sales =
CALCULATE (
    [Total Net Sales],
    Sales[OrderStatus] = "Completed"
)

3 · Advanced

Inactive relationships, a disconnected Targets table, running totals, and blank-aware logic — the patterns that separate a working model from a fragile one.

Measure

Sales trended by ship date, not order date

Ops wants to see the same revenue figure trended by when items actually shipped, not when they were ordered — without breaking the OrderDate-based reports everyone else relies on.

Hint — USERELATIONSHIP activates one of the inactive Date↔Sales relationships for just this one calculation, inside a CALCULATE.

Sales by Ship Date =
CALCULATE (
    [Completed Net Sales],
    USERELATIONSHIP ( 'Date'[Date], Sales[ShipDate] )
)

Try it side by side with Total Net Sales on the same date axis — the two lines will drift apart around month boundaries, since a shipment can land a few days after the order.

Measure

This store's target for the selected month

Targets has no relationship to Date at all — reach across to it manually. For the store and month currently in context, pull back its SalesTarget.

Hint — SELECTEDVALUE(Stores[StoreID]) gets the single store in context (or blank if several are selected). MAX('Date'[Date]) gets the latest date in the current filter, from which you can pull year and month. FILTER + CALCULATE then does the manual lookup that a relationship would normally do for you.

Store Target (Selected Month) =
CALCULATE (
    SUM ( Targets[SalesTarget] ),
    FILTER (
        Targets,
        Targets[StoreID] = SELECTEDVALUE ( Stores[StoreID] )
            && Targets[Year] = YEAR ( MAX ( 'Date'[Date] ) )
            && Targets[Month] = MONTH ( MAX ( 'Date'[Date] ) )
    )
)

This is the general pattern for bridging any disconnected table by matching keys inside CALCULATE — it works whether or not a relationship could exist.

Measure

Promotion attach rate

Roughly two-thirds of Sales rows have a blank PromotionID. Build a measure for what percentage of completed line items actually used a promotion.

Hint — ISBLANK checks PromotionID directly on Sales rather than assuming the Promotions relationship will filter it for you — a blank foreign key still matches nothing on the one side, but you need the count of blanks on the many side.

Promotion Attach Rate % =
VAR PromoLines =
    CALCULATE (
        [Total Line Items],
        Sales[OrderStatus] = "Completed",
        NOT ISBLANK ( Sales[PromotionID] )
    )
VAR CompletedLines =
    CALCULATE ( [Total Line Items], Sales[OrderStatus] = "Completed" )
RETURN
    DIVIDE ( PromoLines, CompletedLines )

Calculated table

Store attainment league table

Bring everything from this section together into one calculated table called Store Attainment: one row per store, showing Actual Sales, Target, and Attainment %.

Hint — Same ADDCOLUMNS + VALUES pattern as the Category Performance table in Intermediate — except this time each row's measures depend on the disconnected Targets bridge you built earlier in this section.

Store Attainment =
ADDCOLUMNS (
    VALUES ( Stores[StoreName] ),
    "Actual Sales", [Completed Net Sales],
    "Target", [Store Target (Selected Month)],
    "Attainment %", [Target Attainment %]
)

Takes an existing table and adds new calculated columns to it, evaluated row by row — a common way to build a calculated table.

New customers acquired per month

Uses each customer's first completed order date as their acquisition month — a common building block for cohort and retention analysis.

EVALUATE
VAR FirstOrders =
    SUMMARIZE(
        Sales,
        Sales[CustomerID],
        "FirstOrderDate", CALCULATE( MIN( Sales[OrderDate] ), Sales[OrderStatus] = "Completed" )
    )
RETURN
    SUMMARIZECOLUMNS(
        "YearMonth", FORMAT( SELECTCOLUMNS( FirstOrders, "d", [FirstOrderDate] ), "YYYY-MM" )
    )

Customer recency segments

A VAR-driven SWITCH that turns a raw "days since last order" number into business-friendly labels — try changing the day thresholds and re-running.

EVALUATE
VAR LastOrderByCustomer =
    SUMMARIZE(
        Sales,
        Sales[CustomerID],
        "LastOrderDate", CALCULATE( MAX( Sales[OrderDate] ), Sales[OrderStatus] = "Completed" )
    )
VAR WithSegment =
    ADDCOLUMNS(
        LastOrderByCustomer,
        "DaysSinceLastOrder", DATEDIFF( [LastOrderDate], DATE(2024,12,31), DAY ),
        "Segment",
            VAR d = DATEDIFF( [LastOrderDate], DATE(2024,12,31), DAY )
            RETURN
                SWITCH(
                    TRUE(),
                    d <= 60, "Active",
                    d <= 150, "At Risk",
                    "Lapsed"
                )
    )
RETURN
    SUMMARIZECOLUMNS(
        "Segment", SELECTCOLUMNS( WithSegment, "s", [Segment] )
    )
